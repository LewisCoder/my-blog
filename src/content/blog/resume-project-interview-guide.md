## 1. 项目应该如何定位

### 1.1 推荐项目名称

业务应用方向优先：

> **成控智能客服与证据驱动的问题排查平台**

Agent 基础设施方向优先：

> **可插拔 Agent Harness 与企业智能客服平台**

不建议只写“AI 聊天机器人”，因为这个项目的主要价值不是简单调用大模型，而是把模型、业务工具、上下文、流式状态、权限和证据链组织成可运行的业务系统。

### 1.2 一句话介绍

> 面向成控业务的企业级智能客服与问题排查平台，基于 FastAPI、OpenAI Agents SDK 和 React，接入项目、订单、定额、商品等内部系统，通过工具调用、记忆、RAG 和流式交互完成业务问答，并通过独立的“计划—执行—证据门禁—结论”状态机，结合业务数据、Compass 源码知识和 FAST 日志完成可追踪的问题排查。

### 1.3 这个项目的四个核心卖点

1. **不是单次模型调用，而是完整 Agent 运行时**：有显式装配、能力注册、生命周期、工具过滤、Prompt、Memory、RAG、上下文压缩和 HITL。
2. **不是让模型自由猜答案，而是证据驱动排查**：独立调查状态机把计划、工具结果、证据和结论分开，必要证据不足时输出 blocked，而不是强行给根因。
3. **不是只有后端接口，而是完整交互链路**：包含普通聊天和调查两套 SSE 协议、取消、重放、思考过程展示、调查树和运营后台。
4. **包含企业应用必需的非功能性能力**：CAS/JWT、scope、用户/ IP 限流、会话持久化、敏感字段过滤、反馈、用量统计、日志和观测。

### 1.4 最适合强调的技术难点

| 难点 | 可以讲清楚的内容 |
|---|---|
| 通用能力与业务逻辑解耦 | HarnessBuilder 显式装配；CapabilityManifest 描述元数据；Registry 调度 hooks；业务工具和 Skill 独立扩展。 |
| 大模型灵活性与排查确定性的平衡 | 普通聊天使用 Agent；高风险问题使用独立、受限、可审计的调查状态机。 |
| 流式请求的全生命周期 | producer + Queue、序号、心跳、取消、Redis 帧重放、部分内容保存、MySQL 落库。 |
| 长上下文与用户状态 | Redis 短期记忆、MySQL 会话与摘要、Mem0 长期偏好、输入超预算时压缩。 |
| 企业数据与权限边界 | Principal/scope、RAG owner/public、调查 FAST 上下文、只读工具、敏感价格过滤、日志脱敏。 |

## 2. 简历上怎么写

### 2.1 项目描述模板

> 面向成控业务的智能客服与线上问题排查平台。后端基于 FastAPI 和 OpenAI Agents SDK 构建可插拔 Agent 运行时，接入内部业务 API、Compass 和 FAST；前端基于 React 实现普通聊天、智能排查、知识库及运营看板。系统支持 SSE 流式输出、会话持久化、Memory/RAG、HITL、CAS/JWT、反馈和用量统计。

技术栈可写：

> Python、FastAPI、OpenAI Agents SDK、SQLAlchemy、MySQL、Redis、Mem0、RAG、SSE、Langfuse/OpenTelemetry、React、Vite、Ant Design、Docker、pytest

不必把依赖列表全部堆到简历上，优先保留自己真正能讲清楚的 8～12 项。

### 2.2 推荐简历 Bullet（按实际贡献选择 4～6 条）

#### Agent 运行时方向

- 设计并实现基于 CapabilityManifest、CapabilityRegistry 和生命周期 hooks 的 Agent 能力体系，将 Memory、意图路由、Skill、槽位填充、RAG、Prompt 和上下文压缩接入统一运行链路，并通过 HarnessBuilder 显式管理共享资源与初始化/释放顺序。
- 基于 OpenAI Agents SDK 封装流式 Agent Runtime，统一模型选择、工具白名单、系统 Prompt、RunContext、事件转换和 HITL RunState 恢复，隔离 HTTP 协议与 Agent 执行逻辑。
- 实现 Markdown Skill 注册与意图路由机制，结合关键词、语义召回和模型精排选择技能，按技能动态过滤 FunctionTool，减少无关工具对模型选择的干扰。

#### 智能排查方向

- 设计独立的 InvestigationRuntime，将问题排查建模为 Plan、Step、ToolResult、Evidence 和 Conclusion，支持步骤并发、动态扩步和独立 SSE 事件，避免调查逻辑与普通聊天互相耦合。
- 建立证据门禁和输出校验：聚合内部业务接口、Compass 源码契约及 FAST 日志，必要证据不足时返回 blocked/clarify，不把数据异常直接包装成确定源码根因。
- 将项目、报价、定额、商品、类目和供应商变更等内部接口封装为受限只读工具，并针对定额等场景过滤敏感价格字段，统一参数、错误和业务证据格式。

#### 后端工程方向

- 构建普通聊天 SSE 服务，通过生产者与 Queue 解耦 Agent 执行和 HTTP 输出，实现事件序号、25 秒心跳、主动取消、Redis 帧缓存/断线重放及部分结果保存；会话、消息和摘要持久化至 MySQL。
- 设计分层上下文方案：Redis 缓存短期消息和摘要，MySQL 保存权威会话与滚动摘要，Mem0 管理长期偏好；输入超模型预算时采用滚动摘要与 TokenBudget 组合压缩。
- 接入 CAS Cookie 与 JWT 两种认证方式，基于 Principal/scope 做接口授权，在认证后执行用户/IP 维度限流；Redis 通过 Lua 实现原子令牌桶，内存实现用于单实例和测试。

#### 全栈与运营方向（确实负责时再选）

- 使用 React 和 Ant Design 实现聊天、技能选择、推理摘要、调查步骤树、证据详情、知识治理、反馈、用量和运营看板，并分别维护普通聊天与调查的 SSE 状态。
- 建立消息点赞/点踩、会话星级、用量及身份映射模型，支持个人统计、管理员趋势分析、差评样本和 Excel 导出，为后续业务效果评估提供数据基础。

## 3. 面试时怎么讲

> 这个项目解决的是成控业务查询和问题排查跨系统、链路长的问题。传统方式需要在项目、订单、定额、商品、日志和源码系统之间切换，单纯接一个大模型又容易出现工具选择不稳定、无证据下结论和会话状态难恢复的问题。
>
> 我在项目中主要负责 `[实际职责]`。整体分为普通聊天和智能排查两条链路：普通聊天由 AgentOrchestrator 调用 OpenAI Agents SDK，在执行前后通过 hooks 接入 Memory、意图路由、Skill、槽位、RAG、Prompt 和上下文压缩，再按技能筛选业务工具。智能排查没有复用自由聊天，而是使用独立状态机，把计划、工具执行、证据报告和结论分开，必要证据不足时返回 blocked，并支持 Compass 和 FAST 的进一步排查。

### 3.3 3 分钟版本与节奏

#### 第一段：背景和目标（约 30 秒）

> 项目面向成控智能客服，既处理项目、订单、定额、商品等查询，也处理需要结合多类证据的问题排查。目标不是做一个聊天壳，而是让回答能调用真实业务数据、能追踪执行过程，并在权限和证据边界内工作。

#### 第二段：总体架构（约 40 秒）

> 前端是 React，后端是 FastAPI。启动时由 HarnessBuilder 显式创建数据库、Redis、模型 Client、工具注册表和各能力实例，应用层再通过协议插件接入 RequestContext、认证和限流。数据上，MySQL 保存会话、消息、摘要、反馈和用量；Redis 负责 SSE 帧、短期缓存、槽位和限流；Mem0 负责长期偏好；轻量 RAG 使用 JSON 文档和向量文件。

#### 第三段：普通聊天（约 40 秒）

> `/chat` 请求进入 chat_service 后，由 AgentOrchestrator 创建 RunContext，依次执行 Memory、意图、Skill、槽位、RAG、UserPrompt、压缩和 Checkpoint hooks。随后 AgentFactory 解析系统 Prompt、筛选工具并调用 SDK 的 `Runner.run_streamed`。服务层把 SDK 事件转换为正文和思考事件，同时维护帧序号、心跳、取消、Redis 重放以及最终的 MySQL 落库。

#### 第四段：智能排查和个人重点（约 50 秒）

> 排查链路与普通聊天隔离，因为排查更关注确定性和证据，而不是自由对话。InvestigationRuntime 驱动 Plan 和 Step，业务 Adapter 调用只读业务接口、Compass 和 FAST，再生成证据报告。证据门禁检查关键证据是否充分，不足时输出 blocked 或 clarify；前端按父子步骤展示工具、日志、接口和结论。我在其中具体负责 `[问题、方案、关键代码、结果]`，遇到的最大难点是 `[真实难点]`，通过 `[真实方案]` 解决。

#### 第五段：结果与复盘（约 20 秒）

> 项目完成了 `[实际交付范围]`，业务指标是 `[真实数据，没有就不说]`。如果继续迭代，我会优先把 HITL/调查协调状态服务端持久化，给流式 Queue 增加背压，将轻量 RAG 替换为可扩展向量存储，并把已有模型弹性和 HTTP 观测组件真正接入主链。

## 4. 高频追问与回答示例

## A. 项目价值与个人贡献

### Q1：这个项目到底解决了什么问题？为什么不直接问 ChatGPT？

**回答示例：**

> 它解决的是企业内部成控数据查询和问题排查，不是开放域聊天。答案依赖项目、订单、定额、商品等内部系统，有时还需要源码契约和 FAST 日志。通用模型没有这些实时数据，也不应直接拥有任意内部系统访问权限。项目通过受限 FunctionTool 获取业务事实，再让模型组织回答；排查场景还增加证据门禁、权限控制和过程展示，因此核心价值是“模型编排 + 企业数据 + 工程控制”，而不是模型本身。

### Q2：你个人负责哪一部分？

**回答模板：**

> 项目整体包含 Agent Runtime、调查状态机、业务工具、存储和前端。我个人主要负责 `[模块]`，独立完成了 `[具体交付]`，与团队协作完成了 `[边界]`。我最熟悉的是 `[关键文件/调用链]`，可以重点展开这部分；其他模块我理解整体设计，但不会把团队工作都归为个人贡献。

最好准备“一个主模块 + 一个辅助模块”，而不是泛泛回答“我负责后端”。

### Q3：项目最大的技术难点是什么？

**推荐回答（选择自己真正做过的部分）：**

> 最大的难点不是调用模型，而是控制不确定性。普通问答可以允许 Agent 自主选工具，但问题排查如果完全自由执行，容易出现参数无来源、证据不足仍给根因、步骤无法复现等问题。因此把调查拆成独立状态机，用结构化 Plan/Step/Evidence 约束过程，参数必须来自用户原文或只读证据，必要证据不足时阻断结论。这是在模型能力和业务可信度之间做的关键权衡。

### Q4：为什么不用一个巨大的 Agent Service 完成所有功能？

**回答示例：**

> 那样会把协议、模型、记忆、工具和业务数据访问揉在一起，后续修改一个能力容易影响整条链路。当前用 App Factory 管 HTTP，用 HarnessBuilder 管资源和生命周期，用 AgentOrchestrator 管一次运行，用 Capability hooks 管横切能力，用独立 InvestigationRuntime 管调查。边界更清晰，也便于替换存储、模型和单项能力。代价是装配代码和概念更多，所以 Manifest 只负责描述，没有再做一个复杂的自动依赖注入框架。

### Q5：项目的实际结果是什么？

**回答原则：**

> 优先说可核验事实，例如“接入了哪些系统”“支持哪些完整流程”“上线到哪个环境”“有多少真实用户/样本”。如果有效率或质量数据，要同时说明统计口径。没有数据时可以说“目前我能确认的是功能交付和技术结果，业务提升比例没有经过严格测量，我不会给出虚假数字”。

### Q6：如果重新做一次，你会改变什么？

**回答示例：**

> 我会更早把运行状态的服务端持久化和多实例约束纳入设计。当前 HITL、Checkpoint、调查互斥仍有进程内状态，轻量 RAG 也不适合大规模数据。其次会把模型弹性和 HTTP 观测直接接入主链，而不是只保留独立模块；同时建立固定业务评测集，持续评估意图路由、工具选择和证据充分性。

## B. Agent、Harness 与上下文

### Q7：Harness、AgentOrchestrator、Capability 分别是什么？

**回答示例：**

> Harness 是组合根和资源容器，负责创建、连接和释放模型 Client、数据库、Redis、工具与能力；AgentOrchestrator 是一次普通 Agent Run 的门面，负责 RunContext、hooks、Agent 创建、SDK 调用和事件输出；Capability 是生命周期或运行阶段的扩展点，例如 Memory 在 BEFORE_RUN 读取上下文、AFTER_RUN 写回消息。三者分别解决“系统如何装配”“一次请求如何执行”“能力如何扩展”。

### Q8：CapabilityManifest 是不是一个自动装配框架？

**回答示例：**

> 不是。Manifest 描述能力名称、类型、依赖、产物和顺序，主要用于目录、健康快照和依赖校验；Registry 负责已注册实例的 hook 分发；真正实例化仍由 HarnessBuilder 或 App Factory 显式完成。这是有意保留的显式装配，避免通过字符串和隐式扫描产生难以追踪的依赖关系。

### Q9：普通聊天 BEFORE_RUN 的执行顺序是什么？为什么这样排？

**回答示例：**

> 当前顺序是 Memory → IntentRouting → Skill → SlotFilling → RAG → UserPrompt → ContextCompression → Checkpoint。先恢复用户上下文，再决定意图和技能；技能确定后才知道需要哪些槽位和工具；之后检索知识、渲染最终用户 Prompt，在调用模型前按输入预算压缩，最后保存运行前快照。顺序由安装顺序和名称确定，不应依赖注册偶然顺序。

### Q10：Skill、意图路由和槽位填充分别解决什么？

**回答示例：**

> Skill 是业务领域声明，包含说明、关键词、Prompt、工具白名单和槽位等；意图路由决定用户问题更适合 chat 还是某个技能，可使用关键词、语义召回和模型精排；槽位填充负责收集订单号、项目 ID 等执行所需参数，缺参时澄清，齐全后把参数注入上下文。它们把“说什么领域”“选哪个流程”“参数是否足够”分开。

### Q11：为什么需要动态工具过滤？直接给模型全部工具不行吗？

**回答示例：**

> 工具越多，名称和描述越相似，模型选择成本和误调用概率越高，也会扩大权限面。项目用 ToolRegistry 管理 audience、审批和启用状态，再根据 Skill/Intent 的 allowlist 构造当前 Agent 的工具集。调查专用工具不会默认暴露给普通聊天。这不是绝对的安全边界，真正的权限和业务校验仍要在工具内部执行。

### Q12：Memory 与上下文压缩是不是一回事？

**回答示例：**

> 不是。Memory 是跨轮、跨会话的上下文管理：Redis 保存短期缓存，MySQL 保存权威会话、消息和滚动摘要，Mem0 保存长期偏好。ContextCompression 只在单次模型输入超预算时工作，用滚动摘要或 TokenBudget 缩减输入。MySQL 会话摘要、Redis 压缩摘要和进程内 Checkpoint 的目的与生命周期都不同。

### Q13：RAG 的检索流程是什么？

**回答示例：**

> 文档先分块、生成 embedding 并保存 owner/public/retrieval 元数据。查询时高相关快路径可以直接返回；否则通过模型扩展多个查询，分别做向量召回、去重，再由模型重排，最后注入用户上下文。当前向量存储是 JSON 文件加 Python 余弦扫描，优势是实现简单、便于验证链路，瓶颈是数据规模和并发，生产扩展时应替换存储而不是继续优化全量文件扫描。

### Q14：为什么 Prompt 要做 Langfuse + YAML 双 Store？

**回答示例：**

> 远端 Prompt 便于运营、版本管理和灰度，但远端故障不应直接导致本地模板全部不可用。CompositeStore 默认 Langfuse 主、YAML 备，Manager 再做 TTL 缓存和 warmup。降级只针对模板获取失败，不能把它误解为模型服务降级。

### Q15：项目是否支持多 Agent Handoff？

**回答示例：**

> 仓库支持基于静态配置创建 SDK 专家 Agent 和 handoff 目标，复用主模型，并有相应示例与测试。但当前普通业务主链主要还是单 Agent + 工具编排，不能声称所有聊天都在多 Agent 协作。Handoff 更适合职责和上下文差异稳定的专家任务，是否启用要评估调试复杂度和状态转移成本。

### Q16：项目是否支持模型 fallback、retry 和 timeout？

**回答示例：**

> 仓库有独立的 ModelRouter 和弹性 Runner，组合方式是总 timeout 包 fallback、fallback 包单模型 retry，并有示例和测试。但普通聊天主链目前直接调用 `Runner.run_streamed`，没有调用 `run_with_resilience`。所以准确说法是“实现了独立弹性组件，尚未接入普通聊天主流程”，不能把配置打开就说主链已经具备容灾。

### Q17：为什么不选择 LangChain/LlamaIndex？

**回答示例：**

> 这个项目的关键需求与 OpenAI Agents SDK 的 Agent、FunctionTool、流式 Runner、Handoff 和 interruption/RunState 比较匹配，因此直接基于 SDK 做薄封装，减少重复实现。项目没有声称在所有维度优于其他框架；如果团队已有 LangChain 生态或需要其检索/集成组件，也可以重新评估。更重要的是把业务工具、会话和能力接口与具体 SDK 隔离，降低替换成本。

## C. SSE、取消、恢复和状态

### Q18：为什么用 SSE，不用 WebSocket？

**回答示例：**

> 当前主要是服务端持续推送正文、思考和调查事件，客户端发送新问题仍走普通 HTTP，双向实时通信需求不强。SSE 基于 HTTP，浏览器支持简单，也便于使用事件序号和重连语义。WebSocket 更适合高频双向通信，但会引入额外连接、协议和运维复杂度。

### Q19：流式输出是怎么实现的？

**回答示例：**

> chat_service 创建后台 producer 消费 `runtime.run_stream()`，把事件转换成带序号的 SSE 帧并放入 Queue，HTTP 协程再从 Queue 输出。25 秒没有普通事件时发送 ping，避免连接长时间无数据。producer 同时负责缓存和最终持久化，HTTP 输出与 Agent 执行因此有一定解耦。当前 Queue 无界，高并发下需要增加容量、超时和背压策略。

### Q20：取消、断线重放和 HITL 恢复有什么区别？

**回答示例：**

> 取消是终止当前生成，结合进程内任务和 Redis 标记，并尽量保存已生成内容；断线重放仍调用 `/chat`，用 `lastEventId` 或 `turnId` 读取 Redis 中的 SSE 帧，缓存 TTL 当前为 600 秒；HITL 恢复调用 `/chat/resume/stream`，依据 SDK RunState 和审批结果继续或终止一次 Agent Run。三者解决的问题完全不同。

### Q21：HITL 是怎么实现的？

**回答示例：**

> SDK 工具调用产生 interruption 后，运行时把 RunState 序列化并返回审批信息。用户批准或拒绝后，恢复接口还原状态；批准会重新运行，拒绝则不再调用模型并执行结束逻辑。当前审批请求和 Checkpoint 都是进程内存，RunState 由客户端回传，适合验证流程，但生产环境还应改成服务端持久化、审批人鉴权、过期控制、签名/防篡改和完整审计。

### Q22：Checkpoint 与 RunState 有什么区别？

**回答示例：**

> Checkpoint 是项目自定义 AgentState 的进程内快照，用于运行前后保存和调试恢复；RunState 是 Agents SDK 的中断运行状态，包含继续执行所需的信息。当前不能拿一个内存 Checkpoint 就跨进程恢复 HITL，也没有完整的生产 Checkpoint 恢复 API。

### Q23：客户端断开后，如何保证消息不丢？

**回答示例：**

> Redis 帧缓存提供有限 TTL 的重放，producer 会把正常结束或部分取消内容写入 MySQL，但这不等于端到端 exactly-once。要应对进程崩溃、多实例和重复提交，还需要服务端 turn 幂等键、持久事件日志、明确提交点、重放游标和重复消息去重。当前实现更准确的描述是“提高断线恢复能力”，不是“绝不丢消息”。

### Q24：流式响应里能看到每一次工具调用吗？

**回答示例：**

> 普通聊天当前直接流式输出正文和推理摘要，工具调用与结果主要在最终 `end.tool_calls` 中汇总；智能排查有另一套更细的 Plan/Step/Evidence 事件。如果普通聊天也要实时工具进度，需要扩展 stream_events 和前端协议，同时注意工具参数和结果中的敏感数据。

### Q25：多实例部署时，取消和恢复还能正常工作吗？

**回答示例：**

> Redis 标记和事件缓存有利于跨请求共享，但活跃 asyncio 任务、审批、Checkpoint 和调查互斥仍有进程内状态，因此不能简单认为任意请求落到任意实例都正确。需要 sticky routing 或取消消息广播，并把运行状态、审批和锁迁移到持久存储/分布式协调组件。

## D. 智能排查与证据链

### Q26：为什么智能排查不做成普通聊天中的一个 Skill？

**回答示例：**

> 普通 Skill 更适合约束某个问答或工具调用，而调查有长生命周期、步骤依赖、动态扩步、证据门禁和独立前端状态。如果塞进普通 Agent，协议和状态会混杂，模型自由决策也更难审计。独立 Runtime 可以明确每一步需要什么输入、产生什么证据、何时允许结论；代价是要维护第二套 SSE 和会话状态。

### Q27：证据门禁如何降低幻觉？

**回答示例：**

> 它把“生成一个看似合理的解释”改成“先满足结构化证据要求”。计划定义必要步骤，工具结果转换为 Evidence，Runtime 和 Adapter 检查必要数据、接口契约和日志证据是否齐全。不足时输出 blocked 或 clarify，不允许把猜测写成确定根因。它不能彻底消除模型错误，因此还需要参数来源限制、输出校验和人工可查看的工具轨迹。

### Q28：Compass 和 FAST 在排查中分别负责什么？

**回答示例：**

> Compass 提供源码搜索、调用链、影响和契约分析，回答“代码应该如何工作”；FAST 提供限定项目和时间窗的日志，回答“实际运行时发生了什么”；内部业务 API 提供项目、订单、报价等事实数据。三类证据相互补充，不能用源码推断代替真实日志，也不能仅凭一条日志就断言业务根因。

### Q29：调查中的动态扩步和并发怎么理解？

**回答示例：**

> 初始计划不是永远固定的，前置只读工具发现新的项目、单据或源码线索后，可以追加后续 Step；相互独立的步骤可以并发执行，有依赖的步骤按状态推进。扩步必须受工具白名单、参数来源、调用预算和证据要求约束，不能变成无限自主探索。

### Q30：基础诊断与最终根因有什么区别？

**回答示例：**

> 基础诊断只识别确定的数据或状态冲突，例如多个值不一致、数量异常、父子单据状态不匹配。它可以明确指出“哪里异常”，但没有源码和日志证据时不能进一步声称“由哪段代码导致”。这种分层让结论措辞与证据强度一致。

### Q31：FAST 查询如何避免变成任意日志/网络访问入口？

**回答示例：**

> 工具不是接收任意 URL 任意查询，而是封装固定服务访问；项目范围、时间窗、关键词和条数有限制，同时做 HTTPS、host、DNS/IP 等安全校验，结果还进行脱敏、去重和每轮预算控制。业务调查上下文还要校验用户权限。具体规则应随部署环境持续做安全审计。

### Q32：如何评估调查功能是否真的有效？

**回答示例：**

> 应建立带标准答案的历史问题集，分别评估参数提取、步骤选择、证据完整性、根因准确性和 blocked 是否合理，并记录平均工具调用数、耗时和人工接管率。当前仓库工程测试较丰富，但不能把单元测试通过等同于排查准确率；如果尚未形成固定业务评测集，应如实说明这是后续重点。

## E. 存储、权限与数据设计

### Q33：为什么同时使用 MySQL、Redis、Mem0 和 JSON 文件？

**回答示例：**

> 它们承担不同一致性和生命周期职责。MySQL 是权威业务数据，保存会话、消息、摘要、反馈和用量；Redis 保存短期缓存、SSE 帧、槽位、压缩摘要和限流状态；Mem0 面向长期偏好记忆；JSON/JSONL 用于轻量 RAG 与知识审核事件。不是存储越多越好，而是当前实现按规模和迭代阶段做了取舍，后续应减少单实例文件和内存状态。

### Q34：会话相关的三张核心表分别做什么？

**回答示例：**

> `chat_sessions` 保存会话及类型、用户等元数据；`chat_messages` 保存角色、内容、轮次等消息记录；`chat_session_summaries` 保存会话滚动摘要。Store 层支持普通/调查类型隔离、软删除、近期消息和摘要读写，消息外键用于级联清理，turn_id 和索引用于轮次关联及查询。具体字段和索引可以从 `docker/mysql/initdb/001_session_store.sql` 与 ORM 模型对照说明。

### Q35：为什么需要用户身份映射？

**回答示例：**

> 系统可能同时出现 ucid 和 account 等身份来源，如果直接按单一字符串统计，同一用户会被拆成多条记录。`user_identity_map` 用于归并身份，让用量、会话和运营看板能按统一用户视角聚合。映射写入和合并仍需注意唯一性、冲突和审计。

### Q36：CAS 和 JWT 分别用于什么场景？

**回答示例：**

> CAS 更适合浏览器 SSO：登录接口校验 ticket、写 session cookie，后续通过 cookie token 获取 Principal；JWT 更适合 Bearer/X-Api-Token 的服务或 API 调用，Backend 验签并校验 exp、issuer、audience、sub 和 scopes。认证插件把 Principal 写入 request.state，后续路由和限流复用。JWT Backend 只验证，不负责签发 token。

### Q37：为什么限流放在认证之后？

**回答示例：**

> 这样可以优先按已认证用户限流，而不只是按 IP，避免 NAT 后多个用户相互影响。插件仍支持路由覆写、用户/IP 维度、429 和响应头。Redis Lua 保证令牌桶计算原子性；Memory backend 只适合单实例或测试。认证失败和匿名请求的策略仍要结合具体路由配置。

### Q38：如何防止敏感价格或跨用户数据泄露？

**回答示例：**

> 需要多层控制：接口先做 Principal/scope 和资源归属校验；RAG 按 owner/public/retrieval 过滤；Memory 接口校验用户维度；业务工具限制为只读，并在定额等场景过滤价格、金额、成本字段；日志和观测做敏感字段 mask。工具白名单不能替代服务端授权。当前仍应持续审计 Memory 管理接口、RAG 空 owner 语义和客户端 RunState 等边界。

### Q39：Redis 读写分离有什么一致性风险？

**回答示例：**

> 当前客户端写 master、读优先 slave，能分担读压力，但主从延迟下可能出现刚写完读不到，影响短期记忆、槽位或重放等对读己之写有要求的场景。处理方式是按数据语义选择强制读 master、带版本/游标、或接受最终一致，而不是所有 key 都采用同一策略。

## F. 可靠性、测试、部署与演进

### Q40：项目的可观测性做到什么程度？

**回答示例：**

> 核心日志有 Request ID、ContextVar、结构化 JSON、滚动文件和字段脱敏；Langfuse 能力可以初始化 Agent/工具观测并记录 session、user 和输出。但当前 HTTP 协议链只有 RequestContext、Auth、RateLimit，ObservabilityPlugin 没有实际安装，因此不能说 HTTP span 已经全链路生效。后续需要把 HTTP trace、模型调用、工具执行和业务 turn 用统一 ID 关联。

### Q41：怎么做测试，Agent 输出不确定怎么办？

**回答示例：**

> 单元测试用假模型和临时存储验证状态机、权限、事件转换、压缩、RAG 和 Store；集成测试验证协议链和能力装配；真实模型与 Langfuse 等外部测试单独验证。对模型不确定性，应把“代码逻辑是否正确”和“模型效果是否足够好”分开：前者用确定性断言，后者用固定评测集和统计指标。仓库部分外部测试的开关保护和异常转 bool 问题也需要继续修正。

### Q42：项目是否已经有完善的端到端测试？

**回答示例：**

> 有 unit、integration、e2e 和 Node smoke，但不能简单说全部自动化完善。默认 pytest 只收集 unit；部分 integration/e2e 可能访问真实外部服务；两个高级 E2E 文件没有 `test_*` 函数，默认零收集；部分脚本有返回 bool 的假阳性风险。因此面试时应该讲测试结构和改进计划，不报未经验证的通过率或覆盖率。

### Q43：Docker 和前端是怎么部署的？

**回答示例：**

> Vite 构建输出到 `src/static`，FastAPI 根路径直接托管；本地开发则由 Vite 代理到 8080。当前 Dockerfile 只复制已有 `src/static`，不会在镜像内执行 npm build，所以构建流水线必须先生成最新前端产物。Moma/SCF 另有 vendor 依赖、前端构建、ZIP 分片上传和切流脚本。

### Q44：如果流量提高十倍，最先优化什么？

**回答示例：**

> 先测量，不直接猜。重点检查模型首 token 与总耗时、业务工具耗时、Queue 堆积、Redis/DB 延迟和事件缓存大小。架构上优先处理无界 Queue、进程内活跃任务/调查锁、JSON 向量全量扫描，以及 HITL/Checkpoint 单实例状态；然后才是缓存和模型参数调优。优化目标要分别看首 token、完整回答、工具调用和资源占用。

### Q45：普通聊天为什么还没有接入模型弹性？

**回答示例：**

> 独立 Runner 已验证 fallback/retry/timeout，但流式主链接入不是简单包一层函数：需要处理首 token 前后的重试差异、已经输出的内容、工具副作用、usage 合并、取消传播和 fallback 后的事件一致性。当前未接入是事实，后续应先定义流式重试边界，再改造 Runtime，而不是对整条流盲目重复执行。

### Q46：如何保证业务工具调用安全、幂等？

**回答示例：**

> 当前核心业务工具以只读查询为主，从根本上降低模型重复调用产生副作用的风险；再通过参数校验、权限、调用预算和超时控制限制执行。未来加入写操作时，需要审批、幂等键、服务端操作审计、防重放和明确的重试策略，不能沿用只读工具的假设。

### Q47：知识治理为什么采用草稿—审核—撤销？

**回答示例：**

> 用户反馈或业务修正不能直接成为所有用户可见的知识，否则错误或恶意内容会污染 RAG。当前用 JSONL 追加草稿、approve、revoke 等事实，再把审核通过的内容投影到 RAG，撤销时删除，启动时 reconcile。优点是过程可追踪，局限是文件存储和并发能力有限，生产扩大后应迁移到事务型存储和正式审核流程。

## G. 综合设计与行为追问

### Q48：这个项目有哪些不足？

**回答示例：**

> 我会把不足分成四类：状态方面，HITL、Checkpoint、调查互斥和活跃任务仍有进程内状态；规模方面，RAG 是本地 JSON 全量扫描，普通 SSE Queue 无界；主链方面，模型弹性和 HTTP 观测模块尚未真正接入；评估方面，工程测试多于业务效果评测。我不把它包装成已经完全分布式、生产完备的平台，但这些边界也使下一步改造方向比较明确。

### Q49：你遇到过的最难 Bug 是什么？

**回答模板：**

> 必须换成自己真实处理过的问题。推荐按“现象 → 影响范围 → 如何定位 → 根因 → 修复 → 回归测试 → 如何防止复发”回答。不要只说“改了一个配置”，要展示如何利用日志、事件序号、RunState、SQL/Redis 数据或最小复现缩小范围。若没有线上事故，可以讲测试中发现的状态恢复、事件顺序或权限隔离问题。

### Q50：如何避免这个项目变成过度设计？

**回答示例：**

> 判断标准是扩展边界是否对应真实变化。模型 Client、数据库、能力和业务工具确实需要独立生命周期，所以 Builder 和 Runtime 分离有价值；调查与普通聊天的状态差异真实存在，所以独立 Runtime 也有价值。但没有再引入通用自动装配、服务网格或复杂消息总线。后续每增加一层抽象，都应有至少两个真实使用场景或明确替换需求。

### Q51：如何和业务方确认系统有用，而不是演示效果好？

**回答示例：**

> 先选高频、答案可核验的场景，记录人工基线；再用同一批问题比较查询耗时、正确率、转人工率和用户反馈。对调查场景还要抽检证据链，区分“回答听起来合理”和“结论被证据支持”。点踩样本、会话星级和用量数据可用于发现问题，但最终仍需结合标注集和业务复盘。

### Q52：下一步最重要的三件事是什么？

**回答示例：**

> 第一，把 HITL/RunState、审批、调查协调和事件游标做成服务端可恢复、可审计的状态，解除单实例限制；第二，补齐流式背压、模型弹性和 HTTP/工具全链路观测，并定义故障语义；第三，建立真实业务评测集和向量存储升级方案，用数据持续评估意图、工具选择和调查结论。具体优先级仍要根据真实流量和事故风险决定。

## 8. 最推荐的一段收尾

当面试官问“你从这个项目学到了什么”，可以这样收束：

> 我最大的收获是，大模型应用的难点往往在模型之外。模型负责理解、规划和表达，但企业系统还必须回答几个问题：数据从哪里来、工具为什么可以调用、执行到哪一步、证据是否足够、断线后如何恢复、用户是否有权限、失败时如何观测。这个项目让我从“让 Agent 能回答”进一步实践到“让 Agent 的回答可追踪、可限制、可恢复、可评估”。同时我也更清楚地看到当前实现距离分布式生产系统还有哪些差距，以及下一步应该优先补哪些能力。
