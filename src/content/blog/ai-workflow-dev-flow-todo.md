> **B点目标**：需求从 ONES 流进来，产物在 git 里生长，决策以飞书卡片形式流到我面前，代码和部署在 agent 侧完成。
> 我每天的工作 = 回答五个问题、签三次字、裁决一次例外，每周让系统变聪明一点。
>
> **主线**：先立协议 → 会话内用真实需求跑通全链 → 人的通道搬飞书 → 指挥搬出会话 → 终验。
> **建设方式**：需求牵引——P2 起选定试点需求①，流水线建到哪儿，需求走到哪儿，不"建完了再用"。
> **总量级**：约 20~30 人日，每天 1~2 小时，横跨 6~8 周。
>
> **用法**：完成一项勾一项；每个阶段必须达成"出口标准"才进入下一阶段。

## 总览

| 阶段 | 目标 | 量级 | 状态 |
|------|------|------|------|
| P0 准备与体验 | 参考实现变体感，摸清外部依赖 | 1~2 天 | ⬜ 未开始 |
| P1 立协议 | 写出引擎宪法（状态机/模板/证据标准） | 2~3 天 | ⬜ 未开始 |
| P2 前端链 + 项目接入 | 需求①走完 澄清→AC→方案拍板 | 3~4 天 | ⬜ 未开始 |
| P3 执行链 | 需求①代码由 agent 逐任务产出且有证据 | 3~5 天 | ⬜ 未开始 |
| P4 质量与交付链 | 双轴跨模型审查 + 发布闸门生效 | 2~3 天 | ⬜ 未开始 |
| P5 闭环 | 活规格回写 + 复盘提案回流引擎 | 2 天 | ⬜ 未开始 |
| P6 飞书闸门通道 | 人不开终端也能审批（可与 P4/P5 并行） | 2~3 天 | ⬜ 未开始 |
| P7 Conductor 服务化 | 指挥搬出 Claude Code，常驻运行 | 3~5 天 | ⬜ 未开始 |
| P8 终验与推广 | 两个硬标准验收，转入稳态运营 | 2 天+持续 | ⬜ 未开始 |

## P0 准备与体验（1~2 天）

- [ ] 安装 mattpocock/skills，用半天体验 grilling（拷问式需求访谈）的实际手感
- [ ] 安装 OpenSpec，体验 propose → apply → archive 流程和 changes/ 产物结构
- [ ] 通读 superpowers 关键 skill 源码（writing-plans / subagent-driven-development / verification-before-completion）
- [ ] 通读 spec-kit 的 constitution / converge / bug 流设计，摘出可借鉴点
- [ ] 定引擎仓库名与 skill 命名风格（建议：`dev-*` 英文目录 + description 中文触发词）
- [ ] **确认外部依赖①**：ONES 需求列表有无 API / 轮询接口（Keones 流水线 API 已打通，需求侧待确认）
- [ ] **确认外部依赖②**：飞书审批（lark-approval）应用权限是否够用；不够则确定降级方案（lark-im 卡片 + 约定格式回复）
- [ ] **确认外部依赖③**：内网网关上 Agent SDK / `claude -p` 长时间运行的稳定性
- [ ] 选定**试点需求①**：中等大小、边界清晰、不紧急（不拿救火需求当试验田）

**出口标准**：
- [ ] 三个外部依赖各有结论（可行 / 降级方案）
- [ ] 试点需求①确定

## P1 立协议（2~3 天，最值得慢的阶段）

- [ ] 写 `protocol/phases.md`：8 阶段状态机（intake → clarified → spec-approved → design-approved → implementing → reviewed → shipped → archived）
- [ ] 每个闸门写清三件事：审批载体、通过条件、驳回后回退到哪个阶段
- [ ] 写 `protocol/status-schema.md`：阶段、闸门确认记录、template-version、关联仓库预留字段
- [ ] 写 `protocol/evidence.md`：编译 / 单测 / Checkstyle 输出怎么取证、怎么算过
- [ ] 写六个产物模板初稿（先糙后精）：proposal / spec-delta / design / tasks / review / retro
- [ ] 从四家仓库摘出要收编的 prompt 片段并归档：grilling 问法、双轴审查提示词、计划写作标准、TDD 纪律
- [ ] 确定产物目录约定：业务仓库 `docs/workflow/{specs,glossary.md,adr,changes}`

**出口标准**：
- [ ] 能对着 phases.md 口述试点需求①的完整流转：每个闸门谁批、批什么、驳回去哪

## P2 前端链 + 项目接入（3~4 天）

- [ ] 建引擎仓库骨架（protocol / skills / scripts / config），做成 Claude Code plugin 装到本机
- [ ] 实现编排 skill：`dev`（入口调度：定位项目→需求→阶段→导航，只导航不自动驾驶）
- [ ] 实现 `dev-init`：扫描仓库生成 workflow-profile 草稿，人确认
- [ ] 实现 `dev-new`：ONES 需求号 + lark-doc/lark-wiki 拉飞书 PRD + 建 changes 目录
- [ ] 实现 `dev-grill` / `dev-spec` / `dev-design` 三个编排 skill
- [ ] 实现原语 skill：`grilling`（拷问原语）、`handoff`（跨会话续作）
- [ ] thaumas 接入：生成 workflow-profile（技术栈 / 构建测试命令 / CLAUDE.md 入口 / 分支策略 / 挂载 cc-上预发 / commit 格式）
- [ ] 活规格冷启动（可并行，半天）：AI 扫代码生成最小 specs/ + glossary.md 草稿，人工审一遍
- [ ] **需求①实跑**：澄清清单真实回答 → AC 真实确认 → 方案真实拍板
- [ ] 记录模板不够用之处，回改 P1 产物

**出口标准**：
- [ ] 需求①的 changes/ 目录里躺着经我确认的 proposal / specs / design

## P3 执行链（3~5 天，技术难度最高）

- [ ] 实现 `dev-tasks`：任务拆到 2~5 分钟粒度，写明文件路径与验证方式（superpowers 计划写作标准）
- [ ] 实现 `dev-impl`：worktree 隔离 + 构建/测试基线验证 → 逐任务派 subagent → 任务间互审
- [ ] 实现原语 `tdd`（Java 适配版）：新增逻辑测试先行、从 AC 生成、禁止参照实现；存量改动回归测试兜底
- [ ] 实现原语 `evidence-check`：声称完成前强制取证（编译 + 相关单测 + Checkstyle），证据落 evidence/
- [ ] 提交自动化：`[需求][号]` 格式从需求目录名自动取号
- [ ] **需求①实跑**：全部任务由 agent 逐任务完成
- [ ] 统计"被人工大改的任务比例"，作为后续改模板/换模型的依据
- [ ] （P3 末尾或 P7 前）实现 worker headless 化：`claude -p` 派生，先验证质量再验证无人值守

**出口标准**：
- [ ] 需求① tasks 全勾、evidence/ 齐全、commit 链干净

## P4 质量与交付链（2~3 天）

- [ ] 通用化收编现有 review.sh 为引擎脚本
- [ ] 实现 `dev-review`：双轴（Standards 规范轴 / Spec 需求符合性轴）× 跨模型（Kimi/GLM，审查模型 ≠ 编码模型硬规则）并行审查
- [ ] 审查报告落 review/ 目录、引用 AC 编号；修复→复审追加记录，不覆盖
- [ ] 实现 `dev-ship`：发布检查单模板（DB 脚本 / 配置 / 回滚方案）
- [ ] **ship 前置闸门硬校验**：status 未到 reviewed 或检查单未勾完，物理拒绝触发 cc-上预发（代码强制，不靠 prompt）
- [ ] profile 挂载 cc-上预发，部署动作委托项目 skill
- [ ] **需求①实跑**：审查清零 → 人工确认 → 上预发 → 验收

**出口标准**：
- [ ] 需求①上线预发
- [ ] 记录双轴审查价值案例（Spec 轴审出纯 diff 审不出的问题；没有也正常，记录即可）

## P5 闭环（2 天）

- [ ] 实现 `dev-archive`：归档到 changes/archive/ + spec delta 回写活规格 + glossary 更新
- [ ] 实现 `dev-retro`：复盘强制分流——项目经验 → CLAUDE.md/glossary；通用经验 → 引擎提案 proposals.md
- [ ] 实现原语：`glossary`、`adr`、`diagnosing-bugs`
- [ ] **需求①归档**，产出第一批引擎提案
- [ ] 评审第一批提案，至少采纳 1 条进引擎

**出口标准**：
- [ ] specs/ 因需求①长出新内容
- [ ] 至少 1 条提案被采纳进引擎
- [ ] **里程碑：会话内全链贯通（B点的"内容"全部成立，只差"形态"）**

## P6 飞书闸门通道（2~3 天，可与 P4/P5 并行）

- [ ] 定义 5 种卡片模板：澄清问题清单（可逐条回复）/ AC 审批 / 方案审批 / 审查结论确认 / 发布审批
- [ ] 实现回执脚本：飞书回复/审批结果 → 写回 status.md 闸门字段（代码校验，不靠模型转述）
- [ ] 通知分级：闸门卡片 / 告警卡片 / 每日进度摘要（一条，不刷屏）
- [ ] 权限不够则落地降级方案：lark-im 卡片 + 约定格式回复，协议不变
- [ ] 选定**试点需求②**（小需求），至少两个闸门只通过飞书完成

**出口标准**：
- [ ] 需求②的至少两个闸门我没开终端，仅凭飞书完成

## P7 Conductor 服务化（3~5 天）

- [ ] Agent SDK 实现 conductor 常驻进程：只做三件事——读状态、派 worker、闸门挂起/恢复（不写代码不审查）
- [ ] 触发源接入：ONES 新需求（API 轮询或 webhook，按 P0 结论；无 API 则飞书转发链接手动触发）
- [ ] worker 全部 headless + 权限最小化：实现 worker 不能 push；审查 worker 只读；部署只由 conductor 在 ship 闸门后触发
- [ ] 运维①宿主机：开发机常驻或内网服务器
- [ ] 运维②Cookie 自愈：复用 ~/.ones 自动续期机制，失效即飞书告警
- [ ] 运维③模型路由：机器层 ~/.dev-flow/models.json 角色路由 + 可用模型白名单
- [ ] 运维④心跳与告警：每日心跳通知；worker 失败挂起告警，不带病推进
- [ ] 恢复机制验证：杀掉进程重启，需求从 status.md 无损续跑
- [ ] **试点需求③实跑**：从 ONES 进来，全程 agent 推进，我只在飞书出现

**出口标准**：
- [ ] 需求③全程无人值守推进，中途杀进程一次，恢复无损

## P8 终验与推广（2 天 + 持续）

- [ ] **终验①**：一个真实需求全程只通过飞书走完（我不打开 IDE）
- [ ] **终验②**：第二个项目五分钟 dev-init 接入并跑通一个小需求
- [ ] 写一页安装/接入说明（引擎无个人信息，profile 进 git，团队化预留）
- [ ] 建立每周引擎提案评审习惯
- [ ] 建立度量记录：每需求记录 审查 P0/P1 数 / 返工轮次 / 人工大改比例 / 我的闸门耗时
- [ ] 用度量数据决定下一个优化点（持续）

## 贯穿全程的三条纪律

1. **每个阶段的出口标准是"真实需求走了一段"，不是"代码写完了"。** 协议和模板的修改权在试点需求的反馈手里。
2. **自动化永远落后于验证**：会话内跑通 → headless → 服务化，每步只把已证明质量稳定的环节交出去。
3. **闸门用代码强制，不用 prompt 恳求。** 尤其 ship 闸门，从 P4 第一天起就是硬校验。

## 风险与对策

| 风险 | 对策 |
|------|------|
| ONES 需求侧无 API | 降级：飞书转发需求链接手动触发 intake，协议不变 |
| 飞书审批权限批不下来 | 降级：lark-im 卡片回复，P0 就确认 |
| 网关模型不稳 / 审查超时 | 模型路由白名单 + 备选自动切换（review.sh 已有）；worker 失败挂起告警 |
| 存量 Java 代码 AI 改动质量差 | P3 度量"人工大改比例"，超阈值先改任务粒度/模板，再考虑换模型 |
| 协议过度设计 | P1 只写试点需求①用得到的字段，其余留预留位 |
| 无人值守后登录态失效 | P7 运维自愈 + 心跳，失效即飞书告警 |
