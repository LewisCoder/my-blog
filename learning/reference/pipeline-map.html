AI 开发流水线参考卡片

配套课程：第 1 课 · 写一张 Agent 能执行的工单 · 词汇表：术语表

这张卡片把「工单 → 规格/计划 → 实现 → 验证 → 评审与文档」压缩成一页。 每个阶段只回答两件事：产出什么，以及什么条件下才算过关。

五阶段地图

  1. 工单
  2. 规格与计划
  3. 实现
  4. 验证
  5. 评审与文档
阶段输入 → 产出过关的闸门主力
① 工单 需求意图 → 可执行工单 每条验收标准都能对应测试或命令 人来定；AI 可帮拆解
② 规格与计划 工单 + 代码库 → 计划（或 OpenSpec 的 proposal / design / tasks） 人审通过；没有超出工单范围的改动 AI 起草；人来审
③ 实现 计划 + 仓库 → 代码改动 编译通过，改动范围与计划一致 AI 主写；人抽查关键点
④ 验证 改动 + 验收标准 → 测试报告 测试全绿；新测试覆盖每条验收标准 人定标准；AI 写测试并运行
⑤ 评审与文档 diff + 工单 → Review 意见、变更说明 评审意见已处理；说明能脱离 diff 读懂 AI 起草；人签收
核心原则 Claude 只能执行你写下来的东西，也只能验证它跑得动的东西。 工单负责「写下来」，验证命令负责「跑得动」。 Anthropic 最佳实践把这两点视为大多数会话偏离预期的根因。

可执行工单模板

# 工单：<一句话标题>

## 目标
<业务结果，1–2 句。不要写实现方案。>

## 范围
- 做：<本次要交付的最小行为>
- 不做：<明确排除的相邻功能、重构、优化>

## 验收标准
1. 当 <触发条件> 时，<系统> 应 <可观察结果>；可由 <测试/命令> 验证。
2. …（每条都必须是可观察、可验证的）

## 约束
- 技术栈：Java / Spring Boot / JUnit 5 / Maven（按项目实际填写）
- 必须遵守：现有分层结构、命名风格、不新增依赖（除非说明理由）
- 必须运行：<验证命令，例如 mvn -q test>

## 交付物
- 代码改动、测试、一段变更说明（或 PR 描述）

验收标准公式

当 <触发条件> 时，<系统> 应 <可观察结果>；可由 <测试/命令> 验证。

Java 示例：任务创建接口

  • 当 POST /api/tasks 收到 {"title":"买菜"} 时，应返回 201，响应体含 id 与 createdAt；由 TaskControllerTest 验证。
  • 当请求缺少 title 时，应返回 400，错误码为 TITLE_REQUIRED；由 TaskControllerTest 验证。
  • 以上两类行为都必须在 mvn -q test -Dtest=TaskControllerTest 下通过。

反例

「任务创建功能完善，参数校验合理，体验良好。」——没有触发条件，没有可观察结果，没有验证方式，Agent 只能靠猜。

两条可直接复制的提示词

1. 只要计划，不要代码

先只输出实施计划：不要修改任何文件，也不要开始实现。
计划必须包含：
1. 逐条复述验收标准，并写明每一条打算用什么测试或命令验证；
2. 要修改/新增的文件清单与实施顺序；
3. 工单里没说清、需要我先确认的问题；
4. 你注意到的、但超出工单范围的隐患（只列出，不要动手）。

2. 实现后自证

按已确认的计划实现。完成后运行 <验证命令>。
若失败：先诊断根因再修复，不要修改验收标准，也不要跳过失败的测试。
最后按验收标准逐条汇报：每条标准 → 对应测试 → 实际结果。

质量清单

  • 工单能在屏幕一屏内读完（过长就拆成两个工单）。
  • 每条验收标准都能对应至少一个测试或命令。
  • 「不做」至少写了 1 条。
  • 计划中每一步都能映射回某条验收标准。
  • 验证命令是具体可执行的，不是「请确认功能正常」。
  • 你在计划或代码里至少提出过一处修改——你在审阅，而不是盖章。

常见反模式

反模式后果改法
验收标准写成主观词（合理、流畅、完善）无法验证，Agent 自我宣布完成改成「触发条件 + 可观察结果 + 验证命令」
工单过大，一屏写不完计划与 diff 都难以审阅拆成多个小工单，逐个闭环
跳过计划直接让 AI 写码方向错误时代码审阅成本极高先要计划，人审后再实现
让 AI 顺手重构无关代码diff 膨胀，风险不可控「不做」里明确排除，越界问题只记录不动手
规格不是越长越好 独立评估机构 Thoughtworks 在技术雷达中提醒：规格驱动开发的产出容易冗长难审，且流程「精巧但意见化」。保持工单小、验收标准少而硬，比撰写一份完备的规格文档更可靠。 来源
