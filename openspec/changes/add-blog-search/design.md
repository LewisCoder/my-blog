# Design

## Context

- 站点为 Astro 7 静态构建，部署在 GitHub Pages；无适配器、无后端、无客户端框架。现有唯一的交互 JS 是 `BlogPost.astro` 中注入代码复制按钮的原生 `<script>`。
- 内容规模：3 篇已发布文章，Markdown 合计约 68KB；内容集合通过 glob loader 加载，构建期可读取 `post.body`（原始 Markdown），`getPublishedPosts()` 已实现「排除草稿 + 按日期倒序」。
- 当前 3 篇文章的 `pubDate` 完全相同（均为 2026-11-17），因此排序必须有独立于日期的最终稳定键。
- 站点约定：所有链接经 `withBase()`；导航使用 `HeaderLink` 的 active 样式；终端/CLI 视觉语言（`// label`、`$ command`、mono 字体、深色 emerald 主题）；Tailwind v4 主题变量集中在 `src/styles/global.css`。
- 方案实测：Pagefind 1.6.0 在本仓库产物上首搜传输约 160–190KB；Fuse.js 7.5.0 约 8.6KB gz，但中文需自定义分词与低阈值；自建记录级索引实测 53KB 原始 / 22.7KB gz（该测量剔除了代码文本）。

## Goals / Non-Goals

**Goals:**

- 零新增依赖、零后端、零构建脚本改动。
- 中文无空格查询可用，多个查询词 AND 匹配，结果按加权相关度排序且顺序确定。
- 索引懒加载且 gzip 体积 ≤30KB，不影响首屏。
- 视觉与交互贴合现有终端风格；键盘基础可用、可访问。
- 查询支持 `?q=` 深链，并对超长查询设上限。

**Non-Goals:**

- 不做模糊容错 / 错别字纠正、拼音搜索、自动补全、搜索历史、按标签筛选、搜索统计、分页。
- 不索引草稿、`/about/` 或其他非文章页面。
- 不引入 Pagefind / Fuse.js / 外部搜索服务；站点内容增长到需要分块索引时再评估。
- 不做离线缓存 / PWA。

## Decisions

### D1：零依赖自建搜索引擎（而非 Pagefind / Fuse.js）

全站可搜索内容仅 ~23KB gz，而 Pagefind 运行时 + WASM 的固定开销就已超过全部内容；其现成 UI 还需适配终端视觉。Fuse.js 体积尚可，但中文效果依赖自定义分词与阈值调优，且摘要/高亮仍需自写。自建方案只需构建期端点 + 约百行原生 JS，传输最小、完全可控，并复用站点已有的 `<script>` 模式。

备选：Pagefind（中文质量最佳、UI 现成，代价是首载体积与构建后置步骤）；Fuse.js（折中，但中文仍需调教）。

### D2：构建期静态索引端点

在 `src/pages/search-index.json.ts` 用 Astro 静态端点导出 `GET`，产出 `/search-index.json`；数据来自 `getPublishedPosts()`，天然排除草稿。每条记录包含 `id / title / description / tags / pubDate / url / body`。

- `url` 字段 MUST 经 `withBase()` 生成，以便未来配置 `base` 时链接仍然有效。
- 正文处理：去除围栏、标题符、强调符、链接与图片语法与 HTML 标签，**保留代码文本与标识符**，压缩空白。
- 索引文件不加入 sitemap；`/search/` 页面本身按 `@astrojs/sitemap` 现有规则被收录。
- 不在客户端直接抓取 `.md`：源文件不进 `dist`，且会暴露未渲染内容。

备选：客户端运行时拼接全文（无数据源）、服务端索引（无后端）。

### D3：记录级索引结构与体积预算

索引是扁平的文章记录数组而非倒排表；在 3–数十篇量级下，线性扫描 + 字段加权足够快。预算：gzip ≤30KB。

保留代码文本会使索引大于实测的 22.7KB。构建后立即测量；若超出预算，依次采用：压缩连续空白 → 去除代码注释 → 缩减重复的导航性文本。仍超出时停止实现并向用户报告，不得静默丢弃正文内容。

### D4：查询管线

1. 归一化：对查询与文章字段两侧都执行 `NFKC` + 小写。索引只存原文；客户端加载索引后为匹配构建归一化副本，摘要仍从原文截取。
2. 分词：优先 `Intl.Segmenter('zh', { granularity: 'word' })`，且特征检测发生在**每次查询时**（而非模块加载时），便于降级路径可验证。不支持时降级为汉字 bigram + 拉丁词切分。
3. 匹配：所有查询词必须同时出现（AND）；每个词在标题/摘要/标签/正文任一字段出现即算该词命中。
4. 打分：标题 ×10、标签 ×6、摘要 ×3、正文 ×1，按命中次数累加。
5. 排序：相关度降序 → `pubDate` 降序 → `id` 升序。`id` 作为最终稳定键，保证同分同日期时顺序确定。

权重常量集中定义，便于后续调整。

备选：OR 匹配（噪声过大）、AND 失败自动降级 OR（增加不可预测性，v1 不做）。

### D5：摘要与高亮

上下文文本的来源优先级：

1. 正文首个命中位置，向前后扩展到约 60–80 个字符（拉丁词按词边界回退），两端加省略号；
2. 正文无命中时，使用文章摘要（`description`）；若摘要本身命中则定位命中位置，否则取摘要开头；
3. 标题与标签中的命中同样高亮。

若归一化导致无法在原文中定位命中位置（极少数长度变化的情况），退回文章摘要，避免摘要错位。

高亮采用「先 HTML 转义原文，再对转义后文本中的命中片段插入 `<mark>`」的顺序，避免 XSS 与标记破坏。

备选：整段摘要截断（命中感弱）、正则直接替换原文（转义风险）。

### D6：索引懒加载与状态机

首屏不请求索引；首次聚焦或输入时 `fetch(withBase('/search-index.json'))` 一次并缓存于内存（Promise 单例，避免并发重复请求）。带 `q` 参数的深链视为已输入，页面加载时立即请求。

页面状态：空查询提示 → 加载中提示 → 结果 / 无结果提示。加载失败时显示终端风格的错误提示并提供重试。

### D7：URL 深链与查询上限

输入变化经短防抖后以 `history.replaceState` 写入 `?q=`，不产生历史记录堆积；空查询时移除 `q` 参数。页面加载时读取 `q` 并执行查询。

查询长度上限 120 个字符：输入框设置 `maxlength`，深链中更长的 `q` 先截断再执行。查询内容只作为文本处理，渲染前必须转义。

### D8：结果与可访问性

每条结果为原生 `<a>`，内部包含序号、标题、日期 · 标签、上下文文本。输入框有可见 label；结果计数通过 `aria-live="polite"` 播报；`<mark>` 使用 accent 配色。Enter 打开首条结果，Esc 清空并保持焦点；结果可由 Tab 逐个访问。视口 <768px 不自动聚焦。

### D9：文件落点

- `src/utils/search-index.ts`：Markdown 去标记（构建期与测试共用）。
- `src/pages/search-index.json.ts`：索引端点，记录 URL 经 `withBase()` 生成。
- `src/pages/search.astro`：页面结构、终端风格静态骨架与内联脚本入口。
- `src/scripts/search-core.js`：无 DOM 依赖的归一化、分词、匹配、排序、摘要与高亮，供浏览器脚本和单元测试共用。
- `src/scripts/blog-search.ts`：DOM 绑定、索引懒加载、状态文案、URL 与键盘逻辑（由页面 `<script>` 导入，Astro 负责打包）。
- `src/components/Header.astro`：新增「搜索」导航项，复用 `HeaderLink` 与 `withBase()`。
- `tests/search-core.test.mjs`、`tests/search-index.test.mjs`：`node --test` 单元测试。

### D10：不新增依赖、不改构建脚本

搜索索引由 Astro 构建期端点自动生成；`npm run build` 与 GitHub Actions 工作流保持不变。新增 `npm test` 脚本仅调用 Node 内置测试运行器，不引入依赖。

## Risks / Trade-offs

- [自建方案需自行维护排序、摘要、高亮与转义逻辑] → 逻辑集中在单一客户端模块，权重与摘要长度常量化；以规格中的场景作为验收清单逐条验证。
- [`Intl.Segmenter` 在旧浏览器缺失] → 查询时特性检测并降级为 bigram + 子串匹配；检测放在查询路径上，便于在浏览器中覆盖验证。
- [Markdown 去标记的正则对复杂语法可能误伤] → 只处理本站实际使用的语法；构建后人工检查索引文本，保留代码标识符。
- [保留代码文本后索引可能超出 30KB] → 构建后立即测量；按 D3 的压缩顺序处理，仍超出则停下来与用户讨论，不擅自删正文。
- [文章增长后索引超出预算或线性扫描变慢] → 当文章量显著增长时再评估 Pagefind 等分块索引方案。
- [索引暴露正文纯文本] → 仅包含已发布文章，与 RSS / 列表可见范围一致；草稿由 `getPublishedPosts()` 保证排除。
- [高亮引入 XSS] → 强制「先转义后插入标记」，并以含尖括号的查询词做验收。
- [Deep link 中的非法或超长查询] → 120 字符上限 + 截断 + 渲染前归一化，不执行任何 HTML。

## Migration Plan

- 合并即生效：构建产出新增 `/search/` 与 `/search-index.json`，无数据迁移、无配置变更；sitemap 按现有规则新增 `/search/`。
- 回滚：还原对应提交即可恢复原状，站点为纯静态无持久状态。
- 发布后验证：`npm run build` 成功；索引 gzip 体积 ≤30KB；上述规格场景手动走查。
